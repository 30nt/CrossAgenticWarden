# Архитектура

*[English version](architecture.md)*

Один движок, пять ролей, два адаптера, четыре guard'а. Ниже — чем владеет каждый и, что полезнее,
чем ему владеть не позволено.

## Общая форма

```
                    .caw/CAW.md          профиль проекта — форма, а не конфиг
                    .caw/runtime.json    какой провайдер выполняет какую роль
                          │
      запрос ──▶ ┌────────▼───────┐
                 │    caw.mjs     │  протокол · схемы · гейты · состояние · коммиты
                 └───┬────────┬───┘
                     │        │
       ┌─────────────┘        └──────────────┐
       ▼                                     ▼
  .caw/agents/*.md                     .caw/adapters/*/
  чем является каждая роль             как запускается провайдер и что он гарантирует
       │                                     │
       └──────────────▶ CLI провайдера ◀─────┘
                             │
                       .caw/hooks/*.py    guard'ы, связывающие сессию самого оператора
```

## Движок владеет тем, чем не должна владеть модель

Это разделение и есть весь замысел. `caw.mjs` владеет:

- **протоколом** — что отправляется, в каком порядке, с каким промптом;
- **схемами** — каждая роль возвращает JSON, проверяемый против фиксированной формы; неверный
  planning-ответ получает одну ограниченную canonical repair-попытку, после чего остаётся отказом,
  а не поводом для интерпретации;
- **гейтами** — `bash -lc "<ваша команда>"`, и код возврата есть вердикт;
- **состоянием** — очередь это директория; история ревью задачи — файл, который пишет движок;
- **коммитами** — `git add -A` и сообщение, несущее полный текст спеки.

Модель не владеет ничем из этого. Она возвращает JSON и, если это исполнитель, правит файлы. Вся
поверхность на этом заканчивается.

Project-specific дополнения подключаются через версионированный
[API project policies](project-policies.ru.md). Planning policies API v2 классифицируют риск
запроса до enumeration и аттестуют разрешённую population после неё. Поэтому `complete` —
project-owned утверждение, связанное с точным digest population, а не вывод из одного model draw.
Risk class может также потребовать зелёный `gate_full` на стартовом коммите до любого executor;
тогда финальный full gate позволяет отнести регрессию к диапазону этого build. Gate policies API
v2 могут классифицировать project-allowlisted flaky failure, а подтверждение и лимит повторов
остаются под управлением ядра.
Кэш обязательного baseline также учитывает проект: ядро хеширует все свои входы и переиспользует
результат, только если gate policy v2 предоставила совпадающий digest внешних входов.
API v3 добавляет необязательный этап acceptance. Проект сопоставляет criteria, surfaces и
transitions задачи со своими production consumers, scenarios, observables, mutations, evidence
kinds и selectors. Ядро проверяет полноту и требует соответствующее gate evidence, а доменная
matrix остаётся вне ядра.

## Пять ролей

| роль | читает | пишет | что производит |
|---|---|---|---|
| `architect` | репозиторий | ничего в доставке | упорядоченный список атомарных задач + карту покрытия |
| `enumerator` | репозиторий, вывод `index_cmd` | ничего | что запрос **подразумевал**, сказано без плана перед глазами |
| `plan-reviewer` | репозиторий, план | ничего в доставке | дыры в заявленном покрытии |
| `executor` | репозиторий | **дерево доставки** | само изменение |
| `reviewer` | репозиторий | только изолированную поверхность | заполненные слоты с доказательствами |

Энумератор слеп намеренно: его спрашивают, что подразумевает запрос, *до* того, как его может
сформировать план, — поэтому его список является проверкой архитектора, а не эхом.
Его канонический ответ кэшируется в Git-private state. Повторное использование требует точного
совпадения digest запроса, эффективного профиля и policy, canonical authorities, состояния
репозитория, project index, runtime, адаптера, CLI, role instructions, schema и движка. Любое
расхождение даёт обычный cache miss; каждый hit или miss записывается в run manifest.

Каждая строка coverage архитектора называет case, его task и один или несколько точных критериев
`done_when` из этой задачи. Движок назначает стабильные по содержанию ID задачам, требованиям,
cases и связям. Plan-reviewer обязан вернуть один доказанный disposition для каждого ID связи;
отсутствующий, повторный или неизвестный ID делает ответ невалидным. Полный ledger остаётся в
`PLAN.md`, а каждый task spec получает свои acceptance links.

Невалидное каноническое значение architect или plan-reviewer получает один repair-вызов той же
роли. В него входят точный путь и сообщение валидации, исходный запрос к роли и полное отвергнутое
значение. Enumerator не запускается заново, и planning review round не расходуется. Второе
невалидное значение останавливает прогон; обе попытки и диагностика остаются в приватной записи.

Каждая задача также объявляет независимо изменяемые surfaces и одну явную state machine для
каждой surface. Ответственности surfaces и переходы становятся требованиями со стабильными ID.
Движок требует глобально уникальные ID surfaces и конкретную причину неделимости, если в одной
задаче их несколько; иначе архитектор обязан разделить работу.

Ревьюер не выносит вердикт. Перед вызовом движок выдаёт стабильный id каждому пункту
`Must cover`, `Change` и `Done when`. Для каждой строки этого атомарного census ревьюер обязан
вернуть ровно один disposition с evidence. Он также заполняет `broken`, `uncovered`, `weak` и
`noted`, а одобрение выводит скрипт — из того, осталось ли открытым что-то блокирующее. С раунда
2 ему выдают его собственные открытые пункты по id, и по каждому он обязан вернуть `closed`,
`open` или `withdrawn` с тем, что он для этого запустил. Пропущенный id остаётся открытым.

Prompts executor и reviewer начинаются с ограниченного task dossier. У каждой секции есть лимит
байтов, digest и отметка усечения; общий размер тоже ограничен. Dossier содержит contract,
changed files, ограниченный diff, сгруппированные открытые findings, executor claims, acceptance
cases и gate receipt. Это уменьшает повторный context, не закрывая чтение репозитория.

Проверки executor имеют структурированный, но недоверенный формат навигационных claims. Их ссылки
на contract не являются границей acceptance: executor может вернуть пустой список, а ошибочные
семантические ссылки не отбрасывают правильный код. Gate получает от
движка приватные пути для manifest и артефактов. CAW валидирует ссылки, пути, kinds и лимиты,
хеширует принятые файлы и создаёт receipt, связанный с digest доставки. Evidence references
reviewer отличают receipt от claims и от прямого чтения репозитория или экспериментов в
изолированной поверхности.

Движок также передаёт обеим planning roles временную схему evidence. Task reviewer получает
receipt `gate_fast` до commit; финальный receipt `gate_full` появляется только после review и
commit всех задач. Поэтому task contract, требующий последний, образует цикл и должен быть
отклонён на planning как unverifiable. Дополнительные команды до review входят в проектную
композицию fast gate, а не в claims executor или proof-артефакты репозитория.

Открытый carried-пункт, в сохранённом evidence которого процитирован критерий, подтверждает
non-met состояние этого критерия без создания новой дублирующей находки. Если schema-valid ответ
ревьюера противоречит одному из этих ledger, движок восстанавливает тот же baseline ревью и даёт
один вызов на исправление. Второе противоречие останавливает прогон до объединения проходов.

Раунд ревью состоит из primary-прохода и максимум `review_challenger_passes` слепых
challenger-проходов. Fixed policy запускает их всегда; risk policy добавляет их для широких или
рискованных изменений, carried findings либо primary-прохода с blocker. Каждый получает один digest доставки в новой изолированной
поверхности. Движок объединяет census и находки до следующего executor. Спор оставляет carried
пункт открытым; находка только challenger помечается `late-same-baseline` вместе с digest.

Каждый finding называет criterion, surface и transition IDs и стабильный property key. CAW
сохраняет наблюдение каждого прохода и объединяет в один work package для executor только точное
совпадение этих полей. Поэтому provenance не теряется, а сходство текста или общий файл не
склеивают разные дефекты.

Вычисленный результат сохраняется как [запись сертификации](certification.ru.md). Принятие кода и
полная сертификация — разные состояния: потерянная независимая population или недоступная
проверка дают `limited`, а не молчаливый `approved`.

У task delivery две записи. Публичный коммит содержит subject, короткий результат gate/review и
digest аудита. Приватная Git-запись аудита содержит полный task contract и identity доказательств,
связанные одновременно с digest проверенной доставки и staged Git tree.

У weak verification могут быть два project-specific контроля. Source probe доказывает, что
проверка загрузила файлы из изолированной review-поверхности, а positive control — что
`gate_fast` становится красным при известном изменении tracked-файла. Они запускаются до мутаций
reviewer, после чего поверхность восстанавливается. Пара необязательна, но неделима: частичные,
неверные, зависшие или неэффективные контроли делают weak evidence недоступной, а не блокируют
доставку.

## Роли привязываются к адаптерам, и привязки доказываются

`.caw/runtime.json` привязывает каждую роль к провайдеру, модели и уровню reasoning. Само по себе
это объявление доверия не имеет. У каждой роли есть набор требований:

`.caw/CAW.md` отдельно задаёт `planning_independence` и `task_independence`. Режим
`same-provider` допускает любую пару, `different-model` требует другого вендора или модели, а
`cross-vendor` сравнивает стабильного владельца `vendor`, которого сообщает адаптер.
`human-review` отключает соответствующего автоматического reviewer и требует OpenSSH-подписанную
аттестацию точных байтов `PLAN.md` или digest доставки. Аттестация и подпись сохраняются в
Git-приватном `caw/human-reviews/`. Фактические пары и результат проверки сохраняются в каждом
run manifest.

Адаптеры объявляют `modelSelection: explicit-id` и поддерживаемые уровни reasoning. Движок
проверяет привязку до provider-вызова. При `require_role_smoke: true` точная комбинация
provider/model/reasoning/CLI/adapter/engine должна иметь Git-приватное доказательство от
`node caw.mjs smoke <role|all>`; смена модели инвалидирует только затронутую роль.

```js
executor: {
  repositoryRead: 'available', directEdit: 'available', shellExecution: 'available',
  externalToolAccess: 'forbidden', writeScope: 'delivery-tree',
}
```

Адаптер описывает, что его провайдер на самом деле предоставляет, и эти два набора сравниваются
явным **частичным порядком по каждому ключу** — строго более сильное объявление удовлетворяет
более слабому требованию. Например, отсутствующий у Claude редактор удовлетворяет
`directEdit: forbidden-delivery` для планирующих ролей.

Ключ, несущий весь замысел, — `writeScope`:

| значение | смысл |
|---|---|
| `none` | ничего |
| `engine-private-only` | только служебная область движка |
| `shell-residual-delivery` | **шелл всё ещё дотягивается до доставки** — так выглядит отсутствие границы ОС |
| `delivery-tree` | исполнитель, и только он |
| `isolated-review-surface` | копия ревьюера, и ничего за её пределами |

Отказ называет гарантию, а не отсутствующую утилиту. `architect requires
writeScope=engine-private-only; adapter field is shell-residual-delivery` — вот как на Linux
выглядит отсутствующий `bwrap`.

## Пробы: доказательство важнее объявления

Привязка, объявившая пробу, недоступна, пока эта проба не зелена **на данной машине**.
`node caw.mjs probe <provider>` делает живой вызов, который пытается писать внутри границы и
снаружи неё, и сохраняет аттестацию с ключом из провайдера, id пробы, полного дайджеста реализации
адаптера, ОС/архитектуры и канонического пути к исполняемому файлу. Дайджест реализации охватывает
entry point, runner и helper-файлы вместе с их исполняемыми правами.

`cli_version` намеренно **не** входит в этот ключ. Привязка доказательств к точной сборке
приводила к тому, что любое рутинное обновление провайдера отказывало всему пайплайну, пока три
платных вызова не переизмерят механизм, который не менялся. Версия по-прежнему записывается и
сообщается при расхождении; ушёл именно отказ. Неизвестный флаг роняет вызов громко, а имя
инструмента, которого CLI больше не знает, не даёт ничего вместо того, чтобы дать всё, — поэтому
обновление провайдера деградирует шумно или безопасно.

Аттестации истекают через 30 дней.

## Guard'ы связывают оператора, а не пайплайн

`.caw/hooks/` — это Python, подключаемый к собственной агентной сессии оператора через её файл
настроек. Они не часть движка, и движок никогда их не вызывает.

| guard | что отказывает |
|---|---|
| `deny_tasks_bash.py` | запись из шелла в `.caw-tasks/PLAN.md`; на любую другую запись в очередь снимает одобрение |
| `deny_tasks_edit.py` | та же политика через прямые инструменты правки файлов |
| `require_caw_log.py` | запуск пайплайна, в командной строке которого не назван `.caw-logs/` |

Они существуют потому, что инструмент не может защитить собственную очередь: `caw.mjs` владеет ею
и исключает её из каждого своего чтения и записи в git, но не видит ничего другого, что её
трогает. Guard'ы закрывают маршрут через агентную сессию. Рука или скрипт остаются снаружи.

Каждый паттерн в guard'ах записан в POSIX-написании, а вход сначала нормализуется: обратные слэши
становятся прямыми, корень проекта вырезается в том написании, в котором пришёл, а серии слэшей
схлопываются. До появления этой нормализации мимо точного совпадения проходили три
Windows-написания.

## Чего намеренно не существует

- **Никакого самохостинга.** Этот репозиторий правится руками и проверяется запуском на чём-то
  другом. Предыдущая версия работала над собой, и это делало каждый документ о пайплайне
  одновременно продуктом и экземпляром пайплайна.
- **Ни реестра метрик с payload или разговорами, ни отдельного файла состояния очереди, ни
  уровней истории.** `ls .caw-tasks/` — очередь, а `git log` — публичная запись. Компактные
  счётчики без payload сохраняются в приватном Git-пути `caw/metrics/`.
- **Никакой карты выбора области по путям.** Есть три явных уровня: `gate_fast`, `gate_batch` и
  `gate_full`; batch- и full-гейты относятся к очереди и остаются командами проекта.
- **Никакого `--force` у `build`.**
