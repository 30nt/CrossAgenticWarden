# Установка Cross-Agentic Warden

Минимальный агентный пайплайн. Архитектор делит запрос на задачи, исполнитель реализует их по
одной, ревьюер судит каждую, энумератор говорит, что запрос подразумевал, а `caw.mjs` держит всё
это вместе. Роли явно привязаны к доверенным адаптерам провайдеров; движок владеет протоколом,
схемами, гейтами, состоянием и коммитами. Ревьюер может менять только изолированную поверхность,
принадлежащую движку, а менять доставку может только исполнитель.

*[English version](install.md)*

Это руководство по установке, и оно длинное потому, что большая его часть — опасность, в которую
кто-то уже вляпался. [README.md](readme.ru.md) — короткая версия, [WHY.md](why.ru.md) — почему
инструмент такой маленький, а [limitations.md](limitations.ru.md) — что в нём прямо сейчас
доказано, не проверено или сломано.

Два шага этой процедуры вынесены в отдельные файлы, потому что каждый из них — работа, а не шаг:
[gate.md](gate.ru.md) — как написать гейт, который не врёт, а [updating.md](updating.ru.md) — как
перевести вендоренную копию на новую версию.

## Требования

- **Node 18+.**
- **Внешняя граница файловой системы для хоста.** Каждая ограниченная роль — две планирующие,
  исполнитель и ревьюер — работает внутри неё, а хост без границы не публикует ни одной
  ограниченной строки, поэтому preflight отказывает любой команде пайплайна. У Claude две
  реализации этого одного механизма: seatbelt на **macOS arm64** через `/usr/bin/sandbox-exec` и
  **Linux** через **`bubblewrap`** (`bwrap` в `PATH`; `apt install bubblewrap`,
  `dnf install bubblewrap`). Ни то, ни другое не ставится за вас, и одно не подменяет другое.
  **Наличие — не способность:** контейнер Docker по умолчанию содержит `bwrap` и запрещает
  непривилегированный user namespace, который тому нужен, а Ubuntu 24.04 ограничивает тот же
  namespace через AppArmor. Адаптеры запускают помощника один раз, а не ищут файл, поэтому такой
  хост отказывает до трат — но чтобы граница вообще появилась, ограничение надо снять. И **не
  запускайте пайплайн от root на Linux**: измерено в контейнере, случай, утверждающий, что запись
  за пределы review-поверхности запрещена, проходит под обычным пользователем и падает под root.
  Codex — только macOS arm64 (его адаптер по-прежнему называет seatbelt напрямую), поэтому
  Linux-хост выполняет строки Claude и отказывает строкам Codex. Отказ называет гарантию, а не
  недостающую утилиту: `architect requires writeScope=engine-private-only; adapter field is
  shell-residual-delivery` — вот как выглядит отсутствующий `bwrap`.
- **Каждый исполняемый файл провайдера, названный в `.caw/runtime.json`.** Claude резолвится как
  `CAW_CLAUDE` или `claude`; Codex — как `CAW_CODEX` или `codex`. Переопределения путей и учётные
  данные остаются за окружением и никогда не попадают в файл рантайма. Текущий измеренный путь
  Codex для executor/reviewer — macOS arm64 и проба по точной версии: новая версия CLI может
  объявлять те же семантические строки, но остаётся недоступной, пока её собственная проба не
  зелена. Сломанная обёртка npm по умолчанию не заменяется автоматически. Если для Codex нужно
  подготовить аутентификацию, укажите `CAW_CODEX_AUTH_FILE` на обычный приватный файл авторизации.
  Адаптер копирует его в приватный транспорт, ограничивает 1 MiB и удаляет копию, увидев, что тёрн
  начался. Это уборка, а не барьер доступа: от старта дочернего процесса до этого события первая
  shell-команда роли может копию прочитать. Устанавливайте `CAW_CODEX_AUTH_FILE`, только если
  принимаете эту остаточную экспозицию.
- **Зелёные живые доказательства для каждой настроенной привязки, объявившей пробу.** Запустите
  `node caw.mjs probe <provider>` на той машине, которая будет её выполнять. Обновление CLI,
  изменение адаптера, смена исполняемого файла, отсутствующее доказательство или красная проба
  делают привязку недоступной до трат. Это не предупреждение, мимо которого можно пройти.
- **`bash` в `PATH`.** Каждый гейт запускается как `bash -lc "<ваша команда гейта>"` из корня
  репозитория. Это **login**-шелл, поэтому PATH берётся из login-профиля: гейт, которому нужны
  nvm, rbenv или asdf, ведёт себя здесь иначе, чем в вашем шелле. На Windows это значит, что
  должны быть доступны Git Bash или WSL.
- **`python3` в `PATH`, до того как подключать guard'ы.** Хуки написаны на Python. Файл настроек,
  называющий хук, который харнесс не может запустить, — это способ разом лишить сессию и `Bash`, и
  `Edit` (измерено, с двумя удалёнными файлами хуков). Сначала запустите один руками — см. ниже.
- **`pytest`, чтобы проверить guard'ы.** Только для этого шага, и этот шаг — единственная проверка
  того, что подключение состоялось. Должно работать `python3 -m pytest`, а не просто `python3`.
  Чистый Python из macOS command-line-tools может его не содержать. Если не хотите ставить
  глобально, используйте одноразовое окружение вне проекта:

  ```bash
  guard_venv="$(mktemp -d "${TMPDIR:-/tmp}/caw-guard-venv.XXXXXX")"
  python3 -m venv "$guard_venv"
  pytest_python="$guard_venv/bin/python"
  "$pytest_python" -m pip install pytest
  ```

  Каждая строка с `pytest` ниже записана как `"${pytest_python:-python3}"`, поэтому она берёт это
  окружение, если вы его создали, и системный интерпретатор, если нет. Некоторым дистрибутивам это
  не удобство, а необходимость: на Ubuntu 25.04 системный интерпретатор внешне управляемый и
  pytest в нём нет вовсе, так что голая форма там падает.

  Держите этот шелл открытым до раздела **Проверка установки целиком**, затем удалите временное
  окружение. Сами guard'ы по-прежнему работают под `python3`; pytest — только тест их установки.

## Установка

Копируйте вот это, и никогда каталог `.caw/` целиком:

```
caw.mjs
.caw/agents/          пять файлов ролей
.caw/adapters/        доверенные адаптеры провайдеров и раннеры
.caw/hooks/           guard'ы и их тесты
.caw/CAW.md           форма профиля — ваша после заполнения, больше никогда не перезаписывать
.caw/runtime.json      только при первой установке — заполнить все пять строк, при обновлении не трогать
```

Рекурсивное копирование `.caw/` молча заменяет заполненный `CAW.md` пустой формой. Это уже
происходило — при первом обновлении первого настоящего инсталла этого инструмента.

**Держите `.caw/` вне всего, что переписывает файлы.** Инсталл, чей гейт гоняет форматтер по всему
репозиторию, молча форкает вендоренную копию, а собственный `git add -A` пайплайна затем этот форк
коммитит — измерено на одном инсталле, где black переписал четыре из пяти файлов хуков в байты,
которые были ровно `black(upstream)`. Ничто об этом не объявляет: файлы продолжают работать, и
расхождение всплывает конфликтом в тот день, когда upstream трогает один из них. Исключите каталог
в конфиге форматтера, а не памятью.

**Отключите конвертацию переводов строк на источнике; одного `git archive` недостаточно.** На
Windows рабочее дерево держит CRLF, поэтому одинаковое содержимое хешируется по-разному: один
инсталл, сравнивавший через `cmp`, отчитался, что устарел каждый скопированный файл, тогда как
изменились двое. Потянуться за `git archive`, потому что он читает базу объектов, а не рабочее
дерево, — очевидная починка, и её недостаточно: `archive` применяет `core.autocrlf` **исходного**
клона, поэтому клон, выкаченный с ним включённым, льёт CRLF в tar, а цель, у которой он выключен,
индексирует эти байты дословно. Измерено на первой Windows-установке этой версии: разошлись все
четырнадцать blob'ов при том, что совпали все четырнадцать прав доступа, — вот как этот отказ
выглядит из сравнения ниже. Начинайте из корня проекта. При первой установке, когда `.caw/CAW.md`
и `.caw/runtime.json` ещё не принадлежат проекту, возьмите ровно эти пути из remote-tracking ref'а
`main`. `fetch` вы вправе выполнить даже в клоне, в котором работает кто-то другой: он двигает
remote-tracking ref'ы и не трогает ни рабочее дерево, ни индекс, ни выбранную ветку. `pull`
трогает, и запускать его там никогда не ваше дело:

```bash
git -C <clone> fetch --quiet origin
git -C <clone> -c core.autocrlf=false -c core.eol=lf \
  archive --format=tar origin/main -- \
  caw.mjs .caw/agents .caw/adapters .caw/hooks .caw/CAW.md .caw/runtime.json \
  | tar -xf -
```

Это не рекурсивное копирование `.caw/`: архив содержит только шесть названных путей. При
обновлении опустите два файла, принадлежащих проекту, ровно так, как говорит
[updating.md](updating.ru.md).

**Одна лишь идентичность blob'ов не сравнивает права доступа.** Один инсталл нёс `755` на двух
файлах, которые этот репозиторий отслеживает как `644`, и все проверки содержимого на нём прошли:
расхождение оказалось невидимым для процедуры, вся работа которой — искать расхождения. `git
archive` восстанавливает отслеживаемые права; затем проиндексируйте только четыре пути,
принадлежащих CAW, чтобы индекс цели можно было сравнить с деревом источника:

```bash
git add -- caw.mjs .caw/agents .caw/adapters .caw/hooks
```

Сравнивайте права и байты вместе, против того же именованного ref'а:

```bash
diff -u \
  <(git -C <clone> ls-tree -r origin/main -- caw.mjs .caw/agents .caw/adapters .caw/hooks \
      | awk '{print $1, $3, $4}' | sort) \
  <(git ls-files -s caw.mjs .caw/agents .caw/adapters .caw/hooks \
      | awk '$3 == 0 {print $1, $2, $4}' | sort)
```

Пустой вывод — зелёный. Это одно сравнение покрывает байты, права, отсутствующие файлы, лишние
файлы и смешанное обновление адаптера/движка/ролей/хуков. Оно намеренно исключает `.caw/CAW.md` и
`.caw/runtime.json`, потому что при первой установке они переходят во владение проекта.

**На хосте без бита исполнения половина этого предложения про права неверна, и случай с `755`
выше — ровно то, что перестаёт ловиться.** Windows не несёт POSIX-битов прав, поэтому индекс цели
записывает `644` для каждого файла независимо от того, что отслеживает источник, и форк только по
правам невидим для сравнения, которое ничего не печатает и читается как зелёное. Измерено:
собственный тест движка для этого сравнения падает на Windows с утверждением `a mode-only fork is
visible`, которое отсутствует. Читайте зелёный прогон там как покрывающий только байты,
отсутствующие и лишние файлы. Половине про права нужен POSIX-хост, и пока такой не проверил этот
инсталл, обновление, меняющее только права, доезжает до него необъявленным.

Три хука исполняемые, потому что подключены как точки входа; `_common.py` импортируется, а
`test_guards.py` запускается под pytest, поэтому оба — `644`. `chmod +x`, чтобы «починить» эти
два, — это расхождение, а не ремонт: тот инсталл имел всё наоборот и прочитал обновление как
поломку.

Добавьте в `.gitignore`:

```
__pycache__/    # единственный по-настоящему важный: прогон guard-тестов его создаёт, а
                # счастливый путь делает `git add -A` — без этой строки .pyc попадут в коммит
.caw-tasks/     # подстраховка — caw.mjs и так сбрасывает оба после индексации, но простой
.caw-logs/      # `git add -A` рукой или другим инструментом этого не делает
```

Три вещи, на которых `build` отказывается стартовать, и они перепроверяются каждый прогон, а не
задаются однажды: **грязное рабочее дерево**, нахождение на ветке, названной в `main_branch:`, и —
это уже для каждой команды — нахождение не в **корне репозитория**. Только проверка корня
связывает `plan`, поэтому `node caw.mjs plan` на вашей главной ветке отработает до конца и
потратит $3–12.

**Не делайте широкий `git add -A`, пока у задачи есть незавершённое состояние раунда.**
Остановленная задача держит изменения доставки в рабочем дереве, а своё состояние — в
`.caw-tasks/.round-*.json`; `git add -A` ради постороннего коммита с конфигурацией
проиндексирует и доставку. Это случалось дважды во время живой приёмки. CAW корректно отказал в
получившемся несогласованном продолжении, но он не может отменить коммит Git, сделанный вне его
процесса. Сначала завершите или отревьюйте задачу, либо индексируйте пути конфигурации явно. Это
руководство — текущая защита; машинное предупреждение об ушедшем вперёд HEAD поверх сохранённого
состояния раунда — рекомендованное продолжение, а не реализованная защита.

## Заполните `.caw/CAW.md`

Это форма, и её поля — вся конфигурация; комментарии внутри говорят, для чего каждое поле. Две
вещи, на которые она указывает и которые живут здесь: контракт гейта и то, что `gate_full:` можно
оставить пустым — тогда быстрый гейт и есть весь гейт.

Строгая weak verification необязательна. Чтобы её включить, заполните одновременно
`weak_source_probe_cmd` и `weak_positive_control_cmd`; только одно поле считается ошибкой профиля.
Source probe запускается в review-поверхности и печатает только строгий JSON с непустым массивом
`loaded_paths`: абсолютными путями к обычным файлам внутри этой поверхности. Менять файлы ему
нельзя. Positive control запускается там же, меняет существующий tracked-файл и обязан сделать
`gate_fast` красным. Обе команды должны быть короткими: их timeout равен
`gate_fast_timeout_ms`, а при пустом поле — пяти секундам.

У provider-вызовов есть четыре независимых бюджета в том же frontmatter: на всю команду
(`budget_request_calls`), только planning (`budget_planning_calls`), одну задачу
(`budget_task_calls`) и каждую роль (`budget_<role>_calls`; дефисы записываются как подчёркивания).
`budget_unknown_cost_calls` отдельно ограничивает завершённые вызовы без reported денежной
стоимости. Каждое значение — положительное целое; оно проверяется до запуска следующего процесса
провайдера. Конечные значения по умолчанию находятся в поставляемом профиле; проект может задать
меньшие границы расходов.

`review_challenger_passes` задаёт число слепых проходов после primary task review: `1` означает
два прохода всего и является поставляемым значением; допустимо `0..2`. Каждый проход расходует
один reviewer-вызов. `require_role_smoke: true` требует точное доказательство привязки после
смены model, reasoning, CLI, адаптера или движка.

Для человеческой независимости задайте `human_review_allowed_signers` как относительный от
репозитория OpenSSH allowed-signers файл. CAW сам ничего не подписывает: `human-review prepare`
создаёт точный census, человек заполняет и подписывает его байты в namespace `caw-review`, а
`human-review accept` проверяет подпись и неизменность артефакта.

## Привяжите все пять ролей в `.caw/runtime.json`

Файл рантайма явный и закрытый: `architect`, `enumerator`, `plan-reviewer`, `executor` и
`reviewer` каждый называют `provider`, нативную для провайдера `model` и уровень reasoning CAW
`low | medium | high | max`. Никаких наследуемых умолчаний ролей и никаких путей к исполняемым
файлам или учётным данным в этом файле нет.

Каждый поставляемый адаптер объявляет передачу явного model ID и поддерживаемые уровни reasoning
CAW. Model ID передаётся как написан; обязательных алиасов нет.

### Чистая машина только с Claude

Codex не является требованием, когда его не выбирает ни одна строка, — на обоих поддерживаемых
хостах. А вот собственная внешняя граница хоста из раздела **Требования** является, и это то
единственное на этом пути, чего у чистой машины вероятнее всего нет. Убедитесь до того, как
что-либо писать:

```bash
case "$(uname -s)" in
  Darwin) test -x /usr/bin/sandbox-exec && echo "seatbelt present" ;;
  Linux)  command -v bwrap >/dev/null && echo "bubblewrap present" ;;
esac
```

Пустой ответ означает, что каждая команда пайплайна откажет после того, как установка проверится
чистой. Затем на машине, где Claude — единственный провайдер, напишите ровно такой
`.caw/runtime.json`:

```json
{
  "version": 1,
  "roles": {
    "architect": { "provider": "claude", "model": "opus", "reasoning": "high" },
    "enumerator": { "provider": "claude", "model": "opus", "reasoning": "high" },
    "plan-reviewer": { "provider": "claude", "model": "opus", "reasoning": "high" },
    "executor": { "provider": "claude", "model": "sonnet", "reasoning": "high" },
    "reviewer": { "provider": "claude", "model": "opus", "reasoning": "high" }
  }
}
```

Имена `opus` и `sonnet` отправляются в Claude ровно как написаны. Убедитесь, что установленный CLI
их принимает. Если `claude` есть в `PATH` и уже авторизован, переменная окружения провайдера не
нужна. Иначе задайте только `CAW_CLAUDE` — абсолютный путь к исполняемому файлу Claude — и
используйте обычную настройку аутентификации CLI. Не ставьте Codex и не задавайте `CAW_CODEX` или
`CAW_CODEX_AUTH_FILE`; ни одна строка Claude их не читает.

`claude auth status` может сообщать `loggedIn: true`, когда закешированный OAuth-токен уже истёк.
Поэтому команда версии и статус — это требования, а не доказательство аутентификации.
Настоящая проверка авторизации — проба ниже. Если она возвращает HTTP 401 или говорит, что токен
истёк, выполните `claude auth login` интерактивно и перезапустите ту же пробу; не считайте четыре
красные аттестации годными доказательствами.

После заполнения `.caw/CAW.md` запустите пробу восстановления Claude из корня целевого
репозитория. Она делает четыре живых вызова провайдера, которые могут быть платными:

```bash
claude --version                         # или: "$CAW_CLAUDE" --version
node caw.mjs probe claude
```

Правильный прогон отчитывается по всем четырём зелёными:

```text
claude-planning-boundary-v1: green
claude-enumerator-tools-v1: green
claude-executor-delivery-v1: green
claude-review-isolation-v3: green
```

Пути, напечатанные после этих сводок, — привязанные к репозиторию аттестации в приватном для Git
каталоге проб. После команды все четыре файла должны существовать; один не должен вытеснять
другой:

```bash
probe_dir="$(git rev-parse --git-path caw/probes)/claude"
find "$probe_dir" -maxdepth 1 -type f -name '*.json' -print | sort
test "$(find "$probe_dir" -maxdepth 1 -type f -name '*.json' | wc -l | tr -d ' ')" -eq 4
```

Если поставляемый профиль сохраняет `require_role_smoke: true`, также выполните:

```bash
node caw.mjs smoke all
```

Команда делает по одному ограниченному вызову на роль и сохраняет Git-приватное доказательство
точной привязки. Смена одной model или reasoning инвалидирует только её роль.

Отсутствующее, красное или вытесненное доказательство корректно заставляет каждую команду
пайплайна отказать до первого вызова роли и напечатать `node caw.mjs probe claude` как команду
восстановления.

Планирующие роли работают с `writeScope: engine-private-only`: транспорт провайдера и служебная
область писать могут, доставка — нет. Эта область обеспечивается подкреплённым пробой
`os-boundary`; это не `isolated-surface`, потому что никакой записываемой копии репозитория не
создаётся. `os-boundary` называет один механизм с реализацией под каждый хост, и различает их
именно проба: аттестация ключуется операционной системой, каноническим исполняемым файлом и
собственными байтами адаптера, поэтому доказательство seatbelt никогда не засчитывается
bubblewrap, а правка границы обнуляет каждую аттестацию, собранную под ней. Она **не** ключуется
сборкой CLI: то, что измеряет проба, обеспечивается ядром против любой сборки, поэтому обновление
провайдера оставляет зелёное доказательство зелёным, и preflight один раз печатает `probe evidence
for claude was observed on CLI <x>; running <y>` вместо отказа. Та половина контракта, которую
сборка *могла бы* сдвинуть, — отсутствующий шелл энумератора, невхождение внешних инструментов —
держится флагами, которых пока не наблюдает ни одна проба. Зелёная аттестация есть доказательство
о том, что обеспечила ОС, и ни о чём другом; флаги, утверждаемые вокруг неё, не являются
утверждением этого файла. Исполнитель использует тот же механизм ОС с записываемой доставкой, а
ревьюер получает настоящую изолированную записываемую копию. Гарантии ролей сравниваются явным
частичным порядком по каждому ключу, поэтому объявление провайдера, строго более сильное,
удовлетворяет более слабому требованию — например, отсутствующий у Claude редактор удовлетворяет
`directEdit: forbidden-delivery` для планирующих ролей.

И `probe`, и каждый успешный preflight пайплайна печатают блок `UNBOUNDED RUNTIME RESIDUALS` до
первого вызова роли или модели. Это не ошибка, и это не делает зелёную пробу недоступной. Блок
говорит, что роли с шеллом могут читать вне доставки и делать исходящие сетевые запросы;
`externalToolAccess: forbidden` исключает только внешние инструменты, нативные для провайдера.
Долговременный отчёт и условия снятия этих остатков — в [SECURITY.md](../SECURITY.md), который и
назван в печатаемой строке. Это URL, а не путь, ровно по этой причине: установка копирует шесть
путей, и дерево документации в них не входит, поэтому относительный путь резолвился бы относительно
целевого проекта и ничего бы не нашёл.

### Граф вызовов и preflight по всем пяти

Граф вызовов таков: `plan` и `review-specs` каждая вызывают `enumerator`, `architect` и
`plan-reviewer`, а `build` вызывает `executor` и `reviewer`. Этот граф **не** сужает preflight
пайплайна: `plan`, `review-specs`, `build`, `round` и `review` резолвят и проверяют все пять строк
до работы, включая роли, которые они не вызовут. Одна строка — неизвестная, неподдержанная, без
своего исполняемого файла или без актуального зелёного доказательства пробы — поэтому отказывает
каждой команде пайплайна; частично доступная установка инертна, а не является урезанным
пайплайном, способным всё же собирать написанные руками спеки. Команды восстановления намеренно
вне этого гарантийного шлюза: `artifacts list` и `purge` не требуют матрицы, а `probe <provider>`
по-прежнему требует валидного рантайма, доверенного адаптера и резолвящегося целевого
исполняемого файла, но не требует, чтобы гарантии ролей уже были удовлетворены. Легаси-профиль,
содержащий `model_architect`, `model_executor`, `model_reviewer`, `effort` или `permission_mode`,
отклоняется с полной пятистрочной отправной точкой для миграции; перенесите выбор в
`runtime.json`, затем удалите легаси-поля, а не держите два источника истины.

Энумератор связан результатом, а не тем, каким инструментом чтения репозитория пользуется
провайдер. Он обязан читать доставку, пока проба границы ОС по точной версии показывает, что
записи в доставку падают, а записи в приватную область движка проходят. Каждый адаптер по-прежнему
сообщает о доступности шелла, но строка энумератора её не сравнивает. После платной энумерации
движок независимо резолвит структурированный `source` каждого случая против текущего репозитория,
точного человеческого запроса или точного дайджестированного блока `index_cmd`, доставленного в
этот вызов. Один некорректный или выдуманный якорь отбрасывает всю популяцию, записывает
ограниченную диагностику и откатывается к собственному чтению plan-reviewer'а; никакого молчаливого
частичного списка и никакого автоматического платного повтора. Это открывает измеренную привязку
энумератора к Codex, не утверждая, что разрешённый адрес доказывает случай или что возвращённая
популяция глобально исчерпывающа.

## Подключение guard'ов

`.caw/hooks/` содержит три `PreToolUse`-guard'а на той сессии, из которой вы запускаете пайплайн.
Они отказывают записям в `.caw-tasks/`, способным фальсифицировать вердикт, и отказывают запуску
пайплайна, не сохраняющему свой вывод.

**Запустите один руками до подключения**, чтобы отсутствующий интерпретатор был упавшей командой,
а не запертой сессией:

```bash
echo '{}' | python3 .caw/hooks/deny_tasks_edit.py
```

Затем влейте подходящий фрагмент; не перезаписывайте файл клиента, в котором уже есть хуки:

- Сессии Claude: влейте
  [`claude-settings.fragment.json`](../.caw/hooks/fragments/claude-settings.fragment.json)
  в `.claude/settings.json` проекта.
- Сессии Codex: влейте
  [`codex-hooks.fragment.json`](../.caw/hooks/fragments/codex-hooks.fragment.json)
  в `.codex/hooks.json` проекта. Codex сообщает о вызовах шелла и unified-exec как о `Bash`, а о
  патчах файлов — как об `apply_patch`, для которого `Edit|Write` являются документированными
  алиасами матчера.

Оба фрагмента проверяют, что Python и названная точка входа guard'а существуют, и возвращают
блокирующий код выхода 2, когда это не так. Важнее всего это при смешанном обновлении версий:
молча пропустить отсутствующий guard хуже, чем отказать вызову инструмента.

Хуки снимаются снимком при старте сессии. Перезапустите сессию после вливания. Для Codex слой
`.codex/` проекта сам должен быть доверенным, а точные определения хуков — просмотрены и
подтверждены в `/hooks`; доверие привязано к их хешам, поэтому каждое изменение требует нового
просмотра. Само наличие файла проекта не является доказательством того, что его хуки отработали.
Флаг `--dangerously-bypass-hook-trust` предназначен только для разового вызова, байты хуков
которого проверены независимо, а не для нормального подключения в проекте.

**Затем проверьте, и посмотрите на код возврата** — это приёмочный тест всего, что выше, потому
что четыре его случая читают `settings.json` этой самой установки и утверждают подключение. Guard,
который харнесс никогда не вызывает, — не guard, а отсутствующий `pytest` выходит с 1 и одной
строкой, которую легко прочитать как успех:

```bash
"${pytest_python:-python3}" -m pytest .caw/hooks   # 118 случаев; ещё 4 при подключении к Claude
node --test test/operator-hooks.test.mjs
```

Что они запрещают — чтобы первый прогон не читался как сломанный: запись в `.caw-tasks/PLAN.md`
запрещена совсем, а запись в любую спеку разрешена, но возвращает `approved:` в `false`, так что
`review-specs` придётся судить очередь заново. Чтение `.caw-tasks/` не блокируется никогда, а сам
`caw.mjs` освобождён — guard'ы связывают руки и сессии, а не инструмент, которому очередь
принадлежит. Именно поэтому `plan`, пишущий спеки в `.caw-tasks/`, их не задевает.

Это ограничители только для сессии оператора. Неинтерактивные дочерние процессы провайдеров
используют границу возможностей адаптера; их гарантии никогда не зависят от конфигурации хуков ни
одного клиента. В частности, вызов дочернего процесса Codex отключает хуки явно, поэтому зелёная
проверка `/hooks` у оператора не может быть засчитана как возможность дочернего процесса.

## Сохранение прогона

**Обязательно, и это обеспечивается.** Перенаправляйте человекочитаемый транскрипт в `.caw-logs/`;
`require_caw_log.py` отказывает запуску пайплайна, который не называет этот каталог. Отдельно
движок создаёт приватный ограниченный сайдкар `run-*` с каноническими финальными объектами
провайдера, идентичностями рантайма и адаптера и ограниченными доказательствами отказов. Он
никогда не сохраняет успешный прогресс и потоки инструментов. У патчей восстановления, состояния
раундов, review-поверхностей, проб и файловых транспортов свои явные границы и сроки жизни;
смотрите их через `artifacts list`, а не предполагайте, что каждая запись в `.caw-logs` живёт по
одному правилу.

```bash
mkdir -p .caw-logs
node caw.mjs plan "…" > .caw-logs/plan-$(date +%H%M%S).log 2>&1
```

PowerShell — ставьте метку времени тоже, иначе каждый прогон перезапишет предыдущий:
`node caw.mjs plan "…" *> .caw-logs\plan-$(Get-Date -Format HHmmss).log`

Если транскрипт содержит доказательство, нужное вам дольше локального окна подрезки, скопируйте
его наружу. Сайдкары прогонов хранят двадцать новейших и не более 30 дней. `artifacts list` —
авторитет по тому, что сейчас удерживается и по какому правилу; не предполагайте, что каждая
запись в `.caw-logs` живёт по одному.

## Проверка установки целиком

Детерминированный и guard-наборы доказывают контракты движка и адаптеров и политику оператора. Они
не являются приёмкой живого провайдера. Прогоняйте набор движка из клона-источника CAW — установка
не копирует `test/` — а синтаксические и guard-проверки запускайте из целевого проекта. Они не
тратят денег. Версионированные пробы провайдеров — живые вызовы и могут быть платными. Затем на
рабочей ветке одноразового авторизованного репозитория прогоните маленький настоящий запрос через
ровно ту матрицу, которую собираетесь поддерживать:

```bash
node --check caw.mjs
node --test <clone>/test/*.test.mjs
"${pytest_python:-python3}" -m pytest .caw/hooks
node caw.mjs probe claude              # матрица только с Claude: четыре зелёные аттестации
node caw.mjs plan "<something small and real>" > .caw-logs/smoke.log 2>&1
```

Спеки должны приземлиться в `.caw-tasks/`, а рядом с ними `.caw-tasks/PLAN.md`. Ничего ещё не
запускалось, так что удалите их, если они вам не нужны.

## Когда прогон останавливается

- **У плана кончились раунды, или ревьюер задал вопрос, которого запрос не решает.** Спеки
  сохраняются, а `PLAN.md` несёт `approved: false`. `build` отказывает, пока `review-specs` не
  вернётся чистым и не переставит флаг — или пока вы не переставите его сами, и тогда незакрытые
  дыры остаются в файле, а каждый `build` говорит, что план одобрен рукой. **Отвечайте там, где
  найдёт следующий прогон, и задавайте множества правилом, а не списком.** Ответы — это то, что
  несёт исправленный запрос, а запрос, называющий собственные решения — *записать A, B и C*, —
  протухает в тот момент, когда ответ добавляет D. Одному инсталлу один и тот же вопрос задали
  дважды, с разрывом в два раунда и около $7, второй раз с более длинным алфавитом: *пункт D
  перечисляет пять и был написан до того, как появились G и H*. Породил это сам процесс ответа.
  `записать каждое решение, которое несёт этот запрос` — та же инструкция, замкнутая относительно
  дополнений, и бесплатная.
- **Архитектор отказывает запросу целиком** — это другая остановка, и она не оставляет
  в `.caw-tasks/` **ничего**: ни спек, ни `PLAN.md`. Он делает так с запросом, чей результат —
  вывод (доказать, исключить, измерить, проаудировать): для отчёта нет гейта, поэтому сборка
  прошла бы с любым выводом. Такое запускайте разговором. Это самая вероятная первая остановка на
  дымовом прогоне, так что выбирайте то, что меняет код.
- **Задача не одобрена к тому раунду, на котором прогон останавливается.** Эта остановка — вопрос,
  а не вердикт о задаче, и задаётся он двумя числами, а не прозой: сколько открытых пунктов
  последний раунд **закрыл** и сколько **новых**. `2 closed of 3, 0 new` — это сходящийся цикл, и
  он хочет ещё раунд; `0 closed of 3, 4 new` — это ревьюер, рисующий заново, и он хочет ваших рук.
  Ничего не закоммичено, дерево держит работу, спека остаётся в очереди, а история ревью
  сохранена — поэтому оба ответа переносят открытые пункты вперёд вместо чтения с чистого листа:
  - `node caw.mjs round <spec>` — **один** дополнительный раунд: исполнитель против этих пунктов,
    затем ревьюер. Он снова остановится и спросит, так что третий раунд — это третье решение.
  - исправьте открытые пункты сами, оставьте работу в дереве, затем `node caw.mjs review <spec>` —
    ревьюер судит то, что вы сделали, и больше ничего не запускается. При одобрении он коммитит, и
    коммит говорит, что последний раунд написан рукой. **Задача, законченная руками, всё равно
    получает ревью**, и ради этого команда и существует.

  Обе снова останавливаются для того же решения вместо зацикливания, и обе коммитят при
  одобрении. Запустите `build` снова для остатка очереди.

  `done` никуда не делся и теперь является узким случаем: он убирает спеку из очереди **вообще без
  какого-либо суждения о работе** и отказывает, пока дерево грязное, потому что грязное значит,
  что `review` ещё может сделать лучше. Тянитесь к нему, только когда работа уже закоммичена.
- **`plan` поверх очереди, в которой ещё есть спеки** → отказ. Он бы перенумеровал с 001 и молча
  перемешал два плана.
- **Прогон умирает посреди задачи** → спека на месте, и повторный запуск переделает эту задачу.
  То, что прогон успел заметить, уходит в `.caw-tasks/notes.log`; `plan` и `build` объявляют этот
  файл на входе, и никто, кроме вас, его не удаляет.
- **Исполнитель задачи возвращает `blocked`** → его работа в дереве, а копия записана в
  `.caw-logs/blocked-<task>.patch`. Эту работу никто не судил: гейт по ней не запускался и ревьюер
  её не видел.
- **Полный гейт красный в конце** → каждая задача была закоммичена по своему зелёному быстрому
  гейту, значит, пропустил не быстрый гейт. Скрипт печатает диапазон для `git bisect`.

- **Вызов роли убит на тридцатой минуте** → не возвращается ничего, а потраченное потрачено. Этот
  потолок срабатывал один раз на вызове, который ещё работал, — на архитекторе поверх очереди из
  шестнадцати спек, — так что считайте его потолком, а не диагнозом. Перезапустите с большим:
  `CAW_AGENT_TIMEOUT_MS=5400000 node caw.mjs review-specs "…" > .caw-logs/…`. Миллисекунды,
  положительное целое; всё остальное отказывается стартовать, а не откатывается к умолчанию.
  Прогон под непринятым по умолчанию потолком говорит об этом первой же строкой, поэтому лог
  несёт, под каким потолком он шёл.

Три потолка в `caw.mjs`, потому что ломается три разных вещи: `MAX_PLAN_ROUNDS`,
`MAX_TASK_ROUNDS` (раунды ревью внутри одного `build`) и `MAX_GATE_RETRIES`. Красный гейт не
является раундом ревью и не должен его тратить. `MAX_TASK_ROUNDS` больше не число, на котором
задача умирает, — это место, где прогон без присмотра останавливается, чтобы спросить вас, — а
